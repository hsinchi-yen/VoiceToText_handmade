- 實作重點：
  - 推論：`transcribe-cpp` crate（0.4.1，MIT）＋ `transcribe-cpp-sys`，開 `cuda` 與 `shared` 兩個 feature。用 `shared`（DLL）是為了避開它和 whisper-rs 各自靜態連結一份 ggml 造成符號衝突。**【實作前確認】** (1) README 只寫 Linux 的 CUDA 建置，Windows＋CUDA 能否建置；(2) Rust API 的載入與轉寫呼叫方式；(3) 和 whisper-rs 同一個執行檔共存不衝突。任一項不成立就停下回報，不要改用其他方案。
  - 開一個 crate feature（例如 `tea`），比照 `sensevoice` 的做法。
  - 模型：`TEA-ASR-1.1-Q8_0.gguf`（2,184,763,808 bytes，SHA-256 `2e4aeb45c9e7f421d99909e29e49a54e204d70ed0e77bebc3f18a135d78298d0`，來源 `https://huggingface.co/dorajim15/TEA-ASR-1.1-transcribe-cpp`，MIT）。存放於 `%LOCALAPPDATA%\v2c\models\`；寫進 `models.json`，可以直接下載。開發用的副本已在 repo 的 `models/`（git 忽略）。
  - 輸入 16 kHz 單聲道；超過 30 秒的音訊切成 ≤30 秒的片段依序辨識再接起來（transcribe.cpp 對 Qwen3-ASR 解碼上限 256 token）。
  - 語言固定 `zh`（中英夾雜仍保留英文，以 `tests/fixtures/audio` 驗證）。
  - 輸出要移除 U+E000–U+F8FF（Private Use Area）字元；GGUF 路徑不會自動移除。
  - 輸出已是繁體台灣用語，**不要**再做簡轉繁。幾乎沒有標點，靠潤飾補；潤飾關閉時照原樣輸出。
  - 選擇規則（`select.rs`）：`asr = "tea_asr"` → GPU 允許、CUDA 可用、模型存在時用 TEA，否則 SenseVoice（附原因）；比照 `asr = "breeze"`，明確指定時略過 VRAM 檢查。`asr = "auto"` 維持 Breeze → SenseVoice，**不**考慮 TEA。TEA 不在 CPU 上執行。
  - VRAM 管理（`gpu_guard.rs`）：TEA 與 Breeze 同樣受載入前檢查、執行中監看、閒置卸載、全螢幕與 `heavy_apps` 讓路約束；讓路時改用 SenseVoice。TEA 實際 VRAM 用量沿用「載入前後量差」的實測方式。
  - 設定頁：語音辨識引擎下拉選單為「自動／Breeze-ASR-25／TEA-ASR-1.1／SenseVoice-Small」；模型頁顯示 TEA 模型狀態與下載。
  - 日誌：記錄 provider 名稱 `tea_asr`、載入時間、VRAM、長度、耗時；**絕不記錄辨識文字**。
- 驗收：
  - 舊的 `config.toml`（沒有 `tea_asr`）照常讀取；`asr = "tea_asr"` 能存、能讀、能在設定頁切換並即時生效。
  - 選 TEA-ASR 後按住 RightCtrl 說話，log 出現 `asr="tea_asr"` 並正常出字；VRAM 不足或全螢幕時改用 SenseVoice。
  - `select.rs` 新規則有單元測試；`cargo run -p v2c-cli -- bench --asr tea tests/fixtures/audio` 可跑，並把與 Breeze 的 CER 與耗時比較寫進報告。
  - `docs/local-setup.md` 說明：三個引擎的差異、TEA-ASR 下載位置與 SHA-256、手動放置模型的步驟、如何在設定頁選用、VRAM 用量（實測值）。
- 驗證指令：`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo fmt --all --check`、`cargo run -p v2c-cli --features tea,cuda -- bench --asr tea tests/fixtures/audio`、`cd apps/desktop && npm run tauri build`
